# Audit: eight carried-forward v2.3 patches vs. v3 upstream

Date: 2026-08-10 (fix round 1: corrected same day)

v2.3 needed 21 hand-patched generated Go files to work around spec defects,
protected only by a `.swagger-codegen-ignore` file the generator does not
read — one regeneration away from silent destruction. This audit re-checks
the eight candidates selected for carry-forward against `api/v3.upstream.yaml`
(never `api/swagger.yaml`, which is a build product) using
`scripts/audit_carried_patches.py`. A CONFIRMED verdict gets an
`api/overlay.yaml` entry; an ALREADY-FIXED verdict gets recorded here and
nothing else, so fixed-upstream defects are not carried forward as dead
corrections.

## Correction notice (fix round 1)

**The first pass of this audit was wrong for three candidates, and the
error was in the audit script itself, not in the spec.** The original
`declares_property`/`required` checks looked only at each schema's
top-level `properties`/`required`. v3 composes heavily with `allOf`, so
that missed fields declared inside composition branches:

- **A8 (peakBandwidth) was recorded ALREADY-FIXED. It was not.**
  `peakBandwidth` is declared twice in `api/v3.upstream.yaml` — inside an
  `allOf` branch of `EnhancedTunnelBase` (line ~5281, feeding the
  `EnhancedTunnel` response schema) and inside an `allOf` branch of
  `StaticTunnelCreate` (line ~7375, a request body). `peakBandwidthMbps`
  appears zero times. The top-level-only check saw neither occurrence and
  reported `schemas=[]`. **Corrected verdict: CONFIRMED.**
- **A6:IPSecRedundantTunnel was recorded ALREADY-FIXED (`required=[]`).**
  It inherits `passphrase` and `remoteID` as required via
  `allOf -> IPSecRedundantTunnelPayload -> IPSecRedundantTunnelDetails`,
  invisible to a top-level-only check on `IPSecRedundantTunnel` itself.
  **Corrected verdict: CONFIRMED.**
- **A6:NetworkTunnelIpsecRedundant was recorded ALREADY-FIXED
  (`required=[]`).** Its own inline `allOf` branch declares
  `required: [haTunnelID, rightASN, rightPrivateIP, leftPrivateIP]` —
  invisible to the same top-level-only check. **Corrected verdict:
  CONFIRMED.**

`declares_property()` and `required_fields()` were added to
`scripts/audit_carried_patches.py` to walk the full `allOf`/`oneOf`/`anyOf`
(and `$ref`) composition tree, and every property/required check in the
script now routes through them. A9 (`ASN`/`RemoteASN` type/format) was
**not** changed — it declares `type` directly at the schema's own top
level, so it was never subject to this blind spot, and its ALREADY-FIXED
verdict is confirmed sound both before and after the fix.

The three sections below present the **corrected** audit as the record of
truth. The corrected overlay entries for A8 and the two A6 sub-candidates
use dedicated `transform` functions rather than a plain `set`/`merge`,
because a naive fix at the most obvious location would have been wrong in
each case — see "Why not a simple `set`?" below.

## A3 — address `{id}` (PUT) vs `{addressId}` (DELETE) param name

Not run through the audit script — codegen output does not exist yet
(`api_objects.go` is generated in Task 5, not before). Disposition decided
by inspecting the spec directly instead of by grepping generated code.
Unaffected by the fix-round correction (A3 was never part of the script).

```
A3   address {id} vs {addressId} param name   DEFERRED   cosmetic only; both verbs
     generate working methods. Normalising would presume Q1's answer. Test row
     OA-N05 (update then immediately delete) detects the alternative at runtime.
```

Reasoning: the PUT and DELETE for objects/addresses live on different path
templates in `api/v3.upstream.yaml`, so openapi-generator emits two
independent methods regardless of whether their path parameters are named
`id` or `addressId` — there is no shared struct or interface that requires
the names to match. Normalising the name would silently assert that `{id}`
and `{addressId}` denote the same identifier space, which is exactly open
question Q1 (still unanswered with the API team). Codegen confirmation of
"both methods generate independently" is deferred to Task 5, once
`api_objects.go` exists and the `grep` the design spec proposes can actually
run. No overlay entry is written for A3.

## Why not a simple `set`?

For A4, A5, A6:IPSecSharedSettingsCreate, A10, and A11 a plain `op: set` or
`op: merge` on the schema's own key is sufficient and is what
`api/overlay.yaml` uses. The three corrected candidates needed more care:

- **A8** — `peakBandwidth` is nested inside `allOf` branches on two
  different schemas, not at either schema's top level. A `set` on a fixed
  path can't reach "wherever this property happens to be nested," so
  `A8-rename-peak-bandwidth` registers a `rename_peak_bandwidth` transform
  (in `scripts/build_spec.py`) that walks every named schema's own
  `allOf`/`oneOf`/`anyOf` branches (not `$ref` — a `$ref`'d schema is a
  separate entry the same loop visits on its own turn) and renames the
  property, and its `required` entry, wherever it finds it.
- **A6:IPSecRedundantTunnel** — the defect's real fields
  (`passphrase`/`remoteID` required) live on `IPSecRedundantTunnelDetails`,
  a schema *shared* with the create request body
  (`CreateIPSecRedundantPayload.tunnel1`/`tunnel2` ->
  `IPSecRedundantTunnelPayload` directly). Setting
  `IPSecRedundantTunnelDetails.required` would also loosen the create path,
  where `passphrase` genuinely is supplied by the caller. Instead,
  `A6-ipsec-redundant-tunnel-not-required` runs a `flatten_and_trim_required`
  transform that materializes `IPSecRedundantTunnel` (the GET-response
  shape, reached only via `IPSecRedundantTunnels.tunnel1`/`tunnel2`) into a
  standalone flat object with its own trimmed `required` list, decoupled
  from the shared ancestor schemas the create path still uses unchanged.
  Verified in the built `api/swagger.yaml`: `IPSecRedundantTunnelDetails`
  and `IPSecRedundantTunnelPayload` (the create-side schemas) still require
  `passphrase`/`remoteID`; only the flattened `IPSecRedundantTunnel` does
  not.
- **A6:NetworkTunnelIpsecRedundant** — here the over-declared fields
  (`rightASN`/`rightPrivateIP`/`leftPrivateIP`) live in a *private* inline
  `allOf` branch (an anonymous object literal, not a named/shared schema),
  so no decoupling is needed. `A6-network-tunnel-ipsec-redundant-not-required`
  runs `trim_network_tunnel_ipsec_redundant_required`, which finds that
  inline branch and drops the three fields from its `required` list in
  place, leaving `haTunnelID` required and the properties themselves
  (still usable, just optional) untouched.

Also note: the build-time overlay engine (`_walk` in
`scripts/build_spec.py`) resolves a `path:` as a list of **dict** keys; it
cannot safely address a specific element of a YAML *list* like an `allOf`
branch (indexing into a list under `create=True` would silently overwrite
that list element with `{}`). That is the second, mechanical reason the two
A6 fixes above are transforms rather than `set`/`merge` overlay entries —
there was no safe declarative path to their nested locations even setting
aside the shared-ancestor concern.

### Notable surprise

The A9 ALREADY-FIXED verdicts were not affected by the fix and remain the
most notable surprise from the original pass: the design spec's Step 3
supplies ready-to-use `merge` overlay entries for `ASN`/`RemoteASN` as if
CONFIRMED were assumed, but v3 upstream already declares both as
`type: integer`. No entry was written for A9 in either audit pass.
