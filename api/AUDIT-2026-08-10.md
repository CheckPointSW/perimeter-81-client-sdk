# Audit: eight carried-forward v2.3 patches vs. v3 upstream

Date: 2026-08-10 (fix round 1: corrected same day)

v2.3 needed 21 hand-patched generated Go files to work around spec defects,
protected only by a `.swagger-codegen-ignore` file the generator does not
read — one regeneration away from silent destruction. This audit re-checks
the eight candidates selected for carry-forward against `api/v3.upstream.yaml`
(never `api/swagger.yaml`, which is a build product) using
`scripts/audit_carried_patches.py`. A CONFIRMED verdict gets an
`api/overlay.yaml` entry; an ALREADY-FIXED verdict gets recorded here and
nothing else, so fixed-upstream defects are not carried forward as dead
corrections.

## Correction notice (fix round 1)

**The first pass of this audit was wrong for three candidates, and the
error was in the audit script itself, not in the spec.** The original
`declares_property`/`required` checks looked only at each schema's
top-level `properties`/`required`. v3 composes heavily with `allOf`, so
that missed fields declared inside composition branches:

- **A8 (peakBandwidth) was recorded ALREADY-FIXED. It was not.**
  `peakBandwidth` is declared twice in `api/v3.upstream.yaml` — inside an
  `allOf` branch of `EnhancedTunnelBase` (line ~5281, feeding the
  `EnhancedTunnel` response schema) and inside an `allOf` branch of
  `StaticTunnelCreate` (line ~7375, a request body). `peakBandwidthMbps`
  appears zero times. The top-level-only check saw neither occurrence and
  reported `schemas=[]`. **Corrected verdict: CONFIRMED.**
- **A6:IPSecRedundantTunnel was recorded ALREADY-FIXED (`required=[]`).**
  It inherits `passphrase` and `remoteID` as required via
  `allOf -> IPSecRedundantTunnelPayload -> IPSecRedundantTunnelDetails`,
  invisible to a top-level-only check on `IPSecRedundantTunnel` itself.
  **Corrected verdict: CONFIRMED.**
- **A6:NetworkTunnelIpsecRedundant was recorded ALREADY-FIXED
  (`required=[]`).** Its own inline `allOf` branch declares
  `required: [haTunnelID, rightASN, rightPrivateIP, leftPrivateIP]` —
  invisible to the same top-level-only check. **Corrected verdict:
  CONFIRMED.**

`declares_property()` and `required_fields()` were added to
`scripts/audit_carried_patches.py` to walk the full `allOf`/`oneOf`/`anyOf`
(and `$ref`) composition tree, and every property/required check in the
script now routes through them. A9 (`ASN`/`RemoteASN` type/format) was
**not** changed — it declares `type` directly at the schema's own top
level, so it was never subject to this blind spot, and its ALREADY-FIXED
verdict is confirmed sound both before and after the fix.

The three sections below present the **corrected** audit as the record of
truth. The corrected overlay entries for A8 and the two A6 sub-candidates
use dedicated `transform` functions rather than a plain `set`/`merge`,
because a naive fix at the most obvious location would have been wrong in
each case — see "Why not a simple `set`?" below.

## A3 — address `{id}` (PUT) vs `{addressId}` (DELETE) param name

Not run through the audit script — codegen output does not exist yet
(`api_objects.go` is generated in Task 5, not before). Disposition decided
by inspecting the spec directly instead of by grepping generated code.
Unaffected by the fix-round correction (A3 was never part of the script).

```
A3   address {id} vs {addressId} param name   DEFERRED   cosmetic only; both verbs
     generate working methods. Normalising would presume Q1's answer. Test row
     OA-N05 (update then immediately delete) detects the alternative at runtime.
```

Reasoning: the PUT and DELETE for objects/addresses live on different path
templates in `api/v3.upstream.yaml`, so openapi-generator emits two
independent methods regardless of whether their path parameters are named
`id` or `addressId` — there is no shared struct or interface that requires
the names to match. Normalising the name would silently assert that `{id}`
and `{addressId}` denote the same identifier space, which is exactly open
question Q1 (still unanswered with the API team). Codegen confirmation of
"both methods generate independently" is deferred to Task 5, once
`api_objects.go` exists and the `grep` the design spec proposes can actually
run. No overlay entry is written for A3.

## Why not a simple `set`?

For A4, A5, A6:IPSecSharedSettingsCreate, A10, and A11 a plain `op: set` or
`op: merge` on the schema's own key is sufficient and is what
`api/overlay.yaml` uses. The three corrected candidates needed more care:

- **A8** — `peakBandwidth` is nested inside `allOf` branches on two
  different schemas, not at either schema's top level. A `set` on a fixed
  path can't reach "wherever this property happens to be nested," so
  `A8-rename-peak-bandwidth` registers a `rename_peak_bandwidth` transform
  (in `scripts/build_spec.py`) that walks every named schema's own
  `allOf`/`oneOf`/`anyOf` branches (not `$ref` — a `$ref`'d schema is a
  separate entry the same loop visits on its own turn) and renames the
  property, and its `required` entry, wherever it finds it.
- **A6:IPSecRedundantTunnel** — the defect's real fields
  (`passphrase`/`remoteID` required) live on `IPSecRedundantTunnelDetails`,
  a schema *shared* with the create request body
  (`CreateIPSecRedundantPayload.tunnel1`/`tunnel2` ->
  `IPSecRedundantTunnelPayload` directly). Setting
  `IPSecRedundantTunnelDetails.required` would also loosen the create path,
  where `passphrase` genuinely is supplied by the caller. Instead,
  `A6-ipsec-redundant-tunnel-not-required` runs a `flatten_and_trim_required`
  transform that materializes `IPSecRedundantTunnel` (the GET-response
  shape, reached only via `IPSecRedundantTunnels.tunnel1`/`tunnel2`) into a
  standalone flat object with its own trimmed `required` list, decoupled
  from the shared ancestor schemas the create path still uses unchanged.
  Verified in the built `api/swagger.yaml`: `IPSecRedundantTunnelDetails`
  and `IPSecRedundantTunnelPayload` (the create-side schemas) still require
  `passphrase`/`remoteID`; only the flattened `IPSecRedundantTunnel` does
  not.
- **A6:NetworkTunnelIpsecRedundant** — here the over-declared fields
  (`rightASN`/`rightPrivateIP`/`leftPrivateIP`) live in a *private* inline
  `allOf` branch (an anonymous object literal, not a named/shared schema),
  so no decoupling is needed. `A6-network-tunnel-ipsec-redundant-not-required`
  runs `trim_network_tunnel_ipsec_redundant_required`, which finds that
  inline branch and drops the three fields from its `required` list in
  place, leaving `haTunnelID` required and the properties themselves
  (still usable, just optional) untouched.

Also note: the build-time overlay engine (`_walk` in
`scripts/build_spec.py`) resolves a `path:` as a list of **dict** keys; it
cannot safely address a specific element of a YAML *list* like an `allOf`
branch (indexing into a list under `create=True` would silently overwrite
that list element with `{}`). That is the second, mechanical reason the two
A6 fixes above are transforms rather than `set`/`merge` overlay entries —
there was no safe declarative path to their nested locations even setting
aside the shared-ancestor concern.

### Notable surprise

The A9 ALREADY-FIXED verdicts were not affected by the fix and remain the

supplies ready-to-use `merge` overlay entries for `ASN`/`RemoteASN` as if
CONFIRMED were assumed, but v3 upstream already declares both as
`type: integer`. No entry was written for A9 in either audit pass.

# Round 2 (2026-08-11): rebuilt from the authoritative source

**What triggered this round.** Phase 1 (porting the Terraform provider onto
this SDK) hit 111 build errors where the plan predicted ~38. Investigation
found that round 1's audit above was built from prose in `LEFTOVERS.md` /
`DEVELOPER-GUIDE.md` rather than from the v2.3 hand-patched files
themselves — incomplete (A9 was checked with the wrong test; A7 was never
checked at all) and, for ASN/RemoteASN, resting on an assumption about
generator behaviour that turned out not to hold. Two real defects were
carried into Phase 1 unfixed as a result.

## Methodology: markers, not prose

The authoritative source was always available and was not used: each of the
20 files in `.swagger-codegen-ignore` carries its own hand-edit rationale,
recoverable directly from git history —

```bash
git show main:.swagger-codegen-ignore | grep -v '^#' | grep -v '^$' | sort -u
```

gives the 20 files. `.swagger-codegen-ignore` itself (also from `git show
main:.swagger-codegen-ignore`) turned out to be the *best* source: unlike
grepping each file's own header comment, it groups the 20 files by the 8
underlying tickets/bugs and states the wire-level reason for each group in
one place. Reading each file individually (`git show main:<file>`) confirms
the marker text and catches anything the ignore-file grouping doesn't state
per-file (see the "peakBandwidth" row below for a case where it mattered).

Of the 20 files, **9 carry an explicit `Hand-edited` / `HAND-PATCHED` /
"codegen produced"** comment inside the file itself:
`api_firewall_policy.go`, `model_asn.go`, `model_enhanced_health_check_meta.go`,
`model_ip_sec_redundant_tunnel.go`, `model_ip_sec_shared_settings_create.go`,
`model_network_tunnel_ipsec_redundant.go`,
`model_objects_services_protocol_request_obj.go`,
`model_objects_services_protocol_response_obj.go`, `model_remote_asn.go`.
The other **11** say only `// Code generated by OpenAPI Generator ...
DO NOT EDIT` — no in-file marker at all. All 11 turned out to share one
undocumented (in-file) trait: a JSON tag renamed from `peakBandwidth` to
`peakBandwidthMbps` with the Go field name left as `PeakBandwidth` (a
give-away that the rename was applied after generation, not before it) —
and `.swagger-codegen-ignore`'s BUG-23 section confirms this is exactly
what happened and why, even though the 11 files' own headers say nothing
about it. Nothing else was found to differ from stock in any of the 11.

## Corrections this round makes to the audit's own history

- **A9 was mis-described as "integer width."** The design spec's carried-forward
  table (§4.3) labels it "ASN / RemoteASN integer width," and round 1's
  script checked exactly that: `schema.get("type") != "integer"`. Both
  ASN and RemoteASN declare `type: integer` at their own top level in v3, so
  the check passed and the audit reported ALREADY-FIXED — in both round 1's
  first pass and its since-corrected pass (see the "Notable surprise" note
  above, which is itself now superseded). The type/format check was not
  wrong about what it tested; it was checking the wrong thing. Both schemas
  also carry a sibling `oneOf` of narrower integer ranges, and
  openapi-generator 7.24.0's Go codegen follows that oneOf into a
  wrapper-model shape instead of the sibling `type: integer` — regenerating
  the exact `type ASN struct {}` empty struct BUG-24 exists to fix.
  Confirmed by generating this SDK from `api/v3.upstream.yaml` with no A9
  overlay entry: `model_asn.go` is `type ASN struct {}`.
- **A7 had no check in the original script at all.** It is candidate A7 in
  the design spec's carried-forward table (§4.3: "Object-service protocol
  shape (`anyOf` strict-match failure)"), but the first version of
  `scripts/audit_carried_patches.py` has no A7 record, no `anyOf` check, and
  no mention of it anywhere — not a wrong verdict, an absent one. It was
  simply dropped between the design spec and the script.
- Both `declares_property()`/`required_fields()` (added in round 1, for A8
  and A6) remain correct and unaffected by this round.

## A9 fix and its limit — read before assuming ASN/RemoteASN are drop-in

The overlay fix (`A9-asn-remove-redundant-oneof`,
`A9-remote-asn-remove-redundant-oneof`) removes the redundant `oneOf` so
`type: integer` stands alone, as the dispatch for this round proposed. That
part works and is a strict improvement: generating this SDK afresh, every
field that used to reference `ASN`/`RemoteASN` (`BasicNetwork.asn`,
`DynamicTunnelDetails.remoteASN`, `DynamicTunnelDetailsUpdate.remoteASN`,
`DynamicTunnelUpdateUpdateTunnelsInner.remoteASN`,
`NetworkTunnelIpsecRedundant.rightASN`,
`EnhancedIPSecSharedSettingsCreate.leftASN`,
`IPSecRedundantTunnelDetails.remoteASN` and everything composed from it —
`IPSecRedundantTunnel.remoteASN`, `IPSecRedundantTunnelPayload.remoteASN`,
etc. — and `IPSecSharedSettings.p81ASN` and everything composed from *that*
— `IPSecSharedSettingsCreate.p81ASN`,
`EnhancedIPSecSharedSettingsCreate.p81ASN`,
`EnhancedIPSecSharedSettingsUpdate.p81ASN`,
`CreateIPSecSinglePayload.p81ASN`, `IPSecSingleDetails.p81ASN`,
`IPSecSingleTunnel.p81ASN`) now generates as a plain `int32`/`*int32` field
that correctly carries a real integer end-to-end. Before the fix every one
of those fields was backed by `ASN{}`/`RemoteASN{}` — always the zero value,
guaranteed silent data loss on every read and write.

**But it does not do what the dispatch for this round assumed it would:
`ASN`/`RemoteASN` do not survive as distinct Go type names.**
openapi-generator's Go generator has no mechanism to alias a bare scalar
(`type: integer`/`string`/`number`/`boolean`, no `enum`) schema to a named
Go type — confirmed empirically four independent ways: (1) a from-scratch
minimal spec with a plain-integer named schema referenced by another
schema's property generates no model file for it, just an inlined `int32`;
(2) the same is true with `format: int32` plus `minimum`/`maximum` added;
(3) `--generate-alias-as-model` has no effect — its own `--help` text scopes
it explicitly to "aliases to **map and array** schemas," not scalars; (4) in
this SDK itself, deleting `model_asn.go`/`model_remote_asn.go` and
regenerating leaves them deleted — nothing regenerates them once the `oneOf`
is gone, and `go build`/`go vet` still pass, because the SDK's own generated
code never converts a bare int to `ASN`. The only spec shape that does force
Go codegen to materialize a distinct named integer type is `enum`
(confirmed: `ObjectServiceProtocolOptionsICMPrequest`, `type: integer` +
`enum`, generates `type ObjectServiceProtocolOptionsICMPrequest int32` plus
constants) — not applicable here, since ASN/RemoteASN are continuous ranges,
not enumerable sets, and a fake enum would either reject real values
(strict `UnmarshalJSON` membership check) or misrepresent the contract.

**Concretely:** `perimeter81Sdk.ASN(int32(65010))` and
`perimeter81Sdk.RemoteASN(int32(65010))` — the exact conversions the
`checkpointsase` provider repo already contains at
`resource_enhanced_dynamic_tunnel.go:291`, `resource_enhanced_dynamic_tunnel.go:357`,
and `utils.go:20-22` — do **not** compile against this fix. Proven with a
throwaway compile check (added, run via `go vet`, then deleted per the
verification bar): the failure is `undefined: ASN` / `undefined: RemoteASN`,
not a struct-conversion error, because the type names no longer exist in the
package at all. A second throwaway check confirmed the positive side:
`DynamicTunnelDetails{RemoteASN: int32(65010)}`,
`EnhancedIPSecSharedSettingsCreate{LeftASN: int32(65011)}`, and
`IPSecRedundantTunnel{RemoteASN: int32(65012)}` all compile and round-trip
the assigned value correctly.

**Why this SDK does not instead hand-maintain `model_asn.go`/`model_remote_asn.go`
to force the named type back into existence:** doing so would only move the
problem, not solve it. Every one of the dozen-plus fields listed above would
still regenerate as bare `int32`/`*int32` on every future `generate.sh` run
(the field's Go type is decided by resolving the referenced schema at
codegen time, independent of whether a hand-maintained file happens to also
define a same-named type), so a hand-maintained `model_asn.go` alone would
produce a package with both `type ASN int32` *and* every real usage site
typed as plain `int32` — the two are not assignable to each other without an
explicit conversion at every one of those sites either way. Making it fully
consistent would require hand-maintaining every struct in that list, which
is exactly the 20-hand-patched-file problem this project exists to eliminate
(F2), not a fix for it. This is a genuine openapi-generator Go-codegen
limitation, not a spec defect the overlay can correct, and is recorded here
as a decision point for Task 14 / Phase 1 rather than papered over:
Phase 1's fix is a small, mechanical, already-scoped edit — drop the
`ASN(...)`/`RemoteASN(...)` conversion at the three call sites above and
assign the `int32`/`*int32` value directly.

## A7 design note: why a flat `set`, not a transform

Unlike A8's `peakBandwidth` (nested inside `allOf` branches, requiring a
tree-walking transform) or A6:IPSecRedundantTunnel (needing to decouple a
shared ancestor), both `ObjectsServicesProtocolRequestObj` and
`ObjectsServicesProtocolResponseObj` declare their `anyOf` directly at the
schema's own top level with nothing else alongside it. Replacing the whole
schema value with `op: set` is sufficient — no transform function needed.
The replacement schema is the union of the two `anyOf` members' properties
(`protocol` from both; `valueType`/`value` from `ObjectServiceProtocolTCPUDP`;
`protocolOptions` from `ObjectServiceProtocolICMPRequest`/`Response`), with
only `protocol` required (it is the only property every real wire payload —
tcp, udp, or icmp — actually carries). `protocolOptions` keeps a `$ref` to
the v3-native `ObjectServiceProtocolOptionsICMPrequest`/`...ICMPresponse`
enum/object types rather than falling back to a bare scalar, so the field
keeps real validation. This matches the v2.3 hand-rewritten Go shape field
list, though the *pointer-ness* of `ValueType` differs: v2.3's hand-written
struct declared `ValueType string` (non-pointer, relying on Go's zero value
plus JSON `omitempty`), while this schema marks `valueType` as genuinely
optional, so codegen emits the idiomatic `*string`. Read via
`terraform-provider-checkpointsase/checkpointsase/utils.go:127-140`
(`flattenProtocolsData`), which assigns `ValueType: m["value_type"].(string)`
— a plain string — into the struct literal: that call site will need a
one-line adjustment (take the address, or add a nil check) once Phase 1
builds against this SDK. Recorded here rather than fixed there, per this
dispatch's "do not modify the provider" constraint.
